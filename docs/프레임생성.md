# 프레임 생성 (120Hz) — 코어 옵션 설명과 설정법

네오지오 포켓은 60fps 로 돕니다. 120Hz 화면(갤럭시 Z 폴드6 등)에서는 같은 그림이 두 번씩
보여서 움직임이 60Hz 그대로입니다. 이 코어의 **프레임 생성**은 두 실제 프레임 사이에
**중간 프레임을 합성**해 120Hz 로 내보냅니다.

## 어떻게 만드나 — 픽셀을 섞지 않는다

DLSS·Lossless Scaling 류는 **픽셀**을 보고 움직임을 추정합니다. 픽셀아트(평평한 색면,
8×8 스프라이트, 2장짜리 애니메이션)에서는 이 추정이 흔들려 번지고 뭉개집니다.

이 코어는 **그래픽 칩(K2GE)의 스프라이트표와 스크롤 레지스터**를 두 프레임에서 캡처해,
위치만 반쯤 옮긴 자리에 **같은 타일을 그대로 다시 그립니다.** 모션 벡터를 추정하는 게
아니라 하드웨어가 아는 정확한 좌표를 씁니다. 그래서

- 번짐·고스트가 원리적으로 없습니다 (픽셀은 늘 실제 타일)
- 타일이 바뀌는(애니메이션 프레임이 넘어가는) 조각은 보간하지 않습니다 — 같은 체인
  그룹(메타스프라이트)의 다른 조각들이 한 방향으로 움직이면 같이 따라갑니다
- 순간이동(24px 넘는 점프)·장면 전환(스크롤 32px 넘는 점프)은 보간하지 않습니다
- 표시 도중 스프라이트표나 타일맵을 고쳐 쓰는 프레임, 흑백 모드 프레임은 합성하지 않고
  실제 프레임을 한 번 더 보여 줍니다 (그 순간만 60Hz 와 같음)

## 두 방식 — 예측(기본) / 보간

| 방식 | 하는 일 | 지연 |
|---|---|---|
| **예측** (`predict`, 기본) | 실제 N 을 바로 내보내고, 다음 8ms 슬롯에 **상태를 저장한 채 N+1 을 미리 돌려** N 의 그림을 N+1 쪽으로 반 옮긴 자리에 그린 뒤 상태를 되돌림 (RetroArch 런어헤드와 같은 원리) | **추가 지연 0** |
| 보간 (`interp`) | N-1↔N 사이를 먼저 보여 주고 다음 슬롯에 N | 표시가 **반 프레임(8.3ms) 늦음** |

예측이 틀리는 때는 **입력이 두 폴 사이에서 바뀐 순간**뿐이고, 그때도 틀린 것은 8ms 짜리
합성 프레임 하나의 위치입니다. 그림은 늘 실제 프레임 N 의 것이라 "안 일어난 장면"이
나오지는 않습니다. 격투게임이면 예측을 쓰십시오.

예측 프레임은 소리를 내지 않고(뮤트), 세이브(플래시) 쓰기를 건드리지 않습니다. 링크 케이블이
물려 있으면 예측이 통신 바이트를 먹어 버리므로 그동안은 합성하지 않습니다(60Hz 와 같음).

## 코어 옵션

| 옵션 | 값 | 설명 |
|---|---|---|
| `ngp_framegen` 프레임 생성 (120Hz) | **자동** / 끔 / 켬 | 자동 = RetroArch 의 주사율 설정(Vertical Refresh Rate)이 120Hz(또는 240 같은 짝수 배)일 때만 켬. 런어헤드가 보이면 바로 물러남 |
| `ngp_framegen_mode` 프레임 생성 방식 | **예측** / 보간 | 위 표 |
| `ngp_framegen_mult` 프레임 생성 배수 | **4배 (게임 박자 맞춤)** / 2배 | 예측 = 두 프레임 앞까지 미리, 보간 = 한 프레임 미리 + 반 프레임 늦게. 아래 「4배」 절 |

켜지면 코어가 fps 를 120.5 로 선언합니다(원래 60.25 의 두 배). 화면 왼쪽 아래에
「프레임 생성 켬 — 120Hz 출력」알림이 뜹니다.

> **60Hz 화면에서 「켬」으로 두지 마십시오.** RetroArch 는 코어 fps 가 화면 주사율보다
> 높으면 vsync 를 끄고 소리에 맞춰 돌리므로 화면이 찢어집니다. 「자동」이 안전합니다.
>
> 설정은 120 인데 패널이 60Hz 에 묶여 있으면(삼성 게임 부스터 등) 게임이 반속이 됩니다.
> 코어가 호출 속도를 재서 2초 넘게 60/s 에 머물면 스스로 끄고 「화면이 120Hz 로 돌지
> 않습니다」알림을 띄웁니다. 그 알림이 뜨면 폰 쪽 설정(아래 1번)을 먼저 보십시오.
> 끈 뒤 10초 → 20초 → 40초 뒤에 세 번까지 스스로 다시 시도합니다(패널이 잠깐 60 으로
> 내려갔다 돌아오는 경우를 살리기 위해 — 실측 주사율로 답하는 앱이면 패널이 돌아올 때
> 되살아납니다). 네 번째로 60/s 에 머물면 프레임 생성 옵션을 껐다 켜거나(값이 바뀌어야
> 합니다 — 다른 옵션을 만지는 것으론 안 풀립니다) 게임을 다시 열 때까지 꺼 둡니다.
> 호출 속도가 90/s 이상으로 30초 연속 이어지면 재시도 횟수가 처음으로 돌아갑니다.

## RetroArch 안드로이드에서 120Hz 로 돌리기 (갤럭시 Z 폴드6 기준)

RetroArch 가 **자기 설정값으로** 120Hz 인 줄 알아야 코어의 자동 모드가 켜집니다.
(코어는 RetroArch 의 `video_refresh_rate` 설정값을 봅니다 — 실제 패널이 아니라.)

1. **삼성 설정** → 디스플레이 → 모션 부드럽게 = **적응형**.
   게임 부스터가 RetroArch 를 「게임」으로 분류해 60Hz 로 묶을 수 있습니다 — 게임 부스터
   설정에서 게임 성능/주사율 제한을 풀거나(One UI 7: 게이밍 모션 부드럽게 = 120Hz, 개별
   게임 FPS 제한 끄기), 게이밍 허브 목록에서 RetroArch 를 빼십시오. (삼성 쪽 메뉴 이름은
   버전마다 달라 실제 화면을 보고 맞춰야 합니다.)
2. RetroArch → 설정 → 비디오 → **Threaded Video 끄기** (켜져 있으면 아래 주사율 항목이
   메뉴에 보이지 않습니다. 프레임 페이싱에도 좋지 않습니다.)
3. RetroArch → 설정 → 비디오 → 출력 →
   - **Screen Resolution** 항목이 있으면(2026-08 중순 이후 nightly, 안정판 1.22 엔 없음) `… (120.00 Hz)`
     모드를 고르십시오. 그러면 Vertical Refresh Rate 도 같이 120 으로 기록됩니다.
   - 없으면(안정판) 폰이 이미 120Hz 로 도는 상태에서 **Set Display-Reported Refresh Rate** 를
     누르거나 **Vertical Refresh Rate** 를 직접 120.000 으로 맞추십시오.
   - **Automatic Refresh Rate Switch** 는 끄십시오 (켜져 있고 모드 전환 조건이 맞으면 코어의
     120.5 선언이 이 설정값을 120.5 로 덮어쓸 수 있습니다).
4. 설정 → 프레임 스로틀 → **런어헤드 끄기**. (런어헤드는 「retro_run 1회 = 1프레임」을
   전제해 2배 출력과 맞지 않습니다. 예측 방식이 이미 같은 원리로 지연 0 을 만듭니다.)
5. 게임을 띄우면 「프레임 생성 켬 — 120Hz 출력 (예측)」알림이 뜹니다. 안 뜨면 3번의
   설정값이 120 이 아닌 것입니다.

VSync Swap Interval 은 **자동(1)** 그대로 둡니다. 코어가 120.5 를 선언하므로 RetroArch 가
120Hz 에 0.4% 안으로 맞춰 돌립니다(지금 60.25 를 60Hz 에 맞추는 것과 같은 비율).

> **삼성 폰에서 RetroArch 가 끝내 60Hz 에 머물 수 있습니다.** 공식 RetroArch 안드로이드 빌드는
> 최소 SDK 21 로 컴파일돼 창 프레임레이트 투표(`ANativeWindow_setFrameRate`) 코드가 빠져 있고,
> RetroArch 소스 주석 자체가 「그러면 삼성 기기에선 컴포지터가 60 을 고른다」고 적고 있습니다.
> 모드를 골라도 패널이 60 에 머물면 위의 「화면이 120Hz 로 돌지 않습니다」알림이 뜹니다.
> 그 경우 **앱판(NGPcustumSP)** 을 쓰십시오 — 앱은 자체 창 프레임레이트 요청으로 120Hz 를
> 받아내며(프레임 타이밍 옵션 → 화면 주사율 덮어쓰기 = 120Hz), 같은 프레임 생성이 들어 있습니다.

## 「DLSS 같은 거」는 왜 안 되나

- **DLSS 자체**: NVIDIA RTX + Windows + 게임 엔진이 뎁스·모션벡터를 넘겨주는 통합 SDK 입니다.
  폰에도, 에뮬레이터의 2D 프레임버퍼에도 꽂을 자리가 없습니다. FSR 2/3·XeSS·퀄컴 SGSR2
  같은 템포럴 방식도 같은 이유로 불가합니다.
- **업스케일만 하는 것**(FSR 1, SGSR 1, Anime4K, xBRZ, ScaleFX): RetroArch 셰이더로 이미
  있습니다(FSR 1 은 `edge-smoothing/fsr`, 픽셀아트용은 `edge-smoothing/xbrz`, `scalefx`).
  움직임을 부드럽게 하지는 않습니다.
- **픽셀 기반 프레임 생성**(Lossless Scaling 류): 안드로이드 이식판(LSFG-Android)이 있지만
  앱 간 Vulkan 후킹이 막혀 화면 캡처+오버레이로 돌아 50~80ms 지연이 더해지고, 픽셀아트에서
  번집니다. 격투게임엔 둘 다 치명적입니다.
- **기기 MEMC**: 폴드6에는 Pixelworks 같은 보간 칩이 없고, 삼성 게임 부스터에도 프레임
  보간 기능은 없습니다.
- **AI 보간(RIFE)**: N+1 프레임을 기다려야 해 지연이 1프레임 늘고, 저해상도 픽셀아트에서
  품질 이점이 없습니다.

이 코어의 방식은 「정확한 모션 벡터를 하드웨어에서 얻어 중간 프레임을 만든다」는 점에서
DLSS 프레임 생성이 추정으로 하는 일을 픽셀아트에 맞게 정확히 하는 셈입니다.

## 4배 — 게임 박자 맞춤 (예측 방식)

사무쇼2는 캐릭터(스프라이트)를 **짝수 프레임에만**, 배경 스크롤을 **홀수 프레임에만** 움직입니다(초당 30번씩 —
롬 실측 600프레임: 스프라이트 자리 바뀐 프레임 224장이 전부 한 홀짝, 배경 바뀐 프레임 25장 중 23장이 반대 홀짝).
2배는 「실제 프레임마다 반 프레임 지점 하나」라 새 그림 사이 빈칸 셋 중 하나만 채웠습니다(A, A, A, A+½, B).
4배는 실제 N 을 돌린 직후 N+1·N+2 를 미리 돌려(소리·플래시 섹션을 뺀 상태 저장·복원) 스프라이트·스크롤 각각
「다음에 바뀌는 프레임 K」를 찾고, 지난번 바뀐 때 L(최대 2프레임 전)부터 K 까지를 고르게 나눠 지금 호출(τ=N)과
다음 합성 호출(τ=N+½) 두 장을 만듭니다 — A, A+¼, A+½, A+¾, B. 그림은 실제 N 의 것이고 위치만 옮깁니다(`ss2fg_render2`:
스프라이트·스크롤 목표와 진행도를 따로 받음, 캡처 링 6장 `ss2fg_hist`, 움직임 판정 `ss2fg_motion`).
실제 호출의 그림도 박자에 맞춰 옮기므로 4배에서는 «날것» 실제 프레임이 화면에 안 나옵니다(입력이 바뀌면 다음 실제
변화에서 바로잡힘 — 예측 방식의 성질). 계산량은 2배 대비 약 1.5배(실제 1 + 예측 2).
보간 방식의 4배는 「반반」입니다(`fg_hybrid4`): 화면을 반 프레임 늦게 보여 주면(지금 보간과 같은 +8ms) 다음에 바뀌는
프레임이 늘 N 이나 N+1 이라 한 프레임만 미리 돌리면 됩니다 — 실제 호출에 τ=N-½(바탕 N-1), 합성 호출에 τ=N. 계산량은
예측 2배와 같고, N+1 위치 예측은 게임이 입력을 한 프레임 늦게 반영해 실측 100% 적중(PocketCore 방 f3bc9bf).
(PocketCore 방의 패치 `20_ss2fg_4x.patch`(023a638)를 main 에 들였습니다. 롬 실측: 점프 머리 높이 72→70→69→68 로
한 칸씩, 2배는 72,72→69,69→68. off 모드 기준 프레임 N·N+1·N+2 대조 지표는 2배 합성 프레임과 같은 수준.)

## 검증 (롬 없이 돕니다)

```sh
cd build
# 합성 렌더러 — 원본 K2GE 렌더러와 같은 상태로 비교 (동치·중점·체인·스크롤 랩·래스터·더티 1,500여 건)
gcc -O1 -std=gnu99 -I. -Imednafen -Imednafen/ngp -Ilibretro-common/include -DWANT_16BPP \
    -DFRONTEND_SUPPORTS_RGB565 -DMEDNAFEN_VERSION_NUMERIC=931 -D__LIBRETRO__ -DINLINE=inline \
    -o /tmp/fgtest ../tools/harness/fgtest.c mednafen/ngp/gfx.c ss2fg.c && /tmp/fgtest
# 배관 — 합성 롬으로 코어를 돌려 2배 fps 전환·오디오 분배·예측 후 상태 복원(결정성)·런어헤드 가드 검사
gcc -O1 -std=gnu99 -Ilibretro-common/include -o /tmp/fgsmoke ../tools/harness/fgsmoke.c -ldl \
    && mkdir -p /tmp/fgsmoke.d && /tmp/fgsmoke ./mednafen_ngp_libretro.so /tmp/fgsmoke.d
```

실제 게임 화면에서의 합성 품질(슬롯 안정성, 표시 중 VRAM 쓰기 빈도)은 롬으로 실측해야
합니다 — 폴백이 잦으면 그 구간은 60Hz 와 같게 보입니다.

롬이 있으면 `tools/harness/fgrom.c` 로 실측할 수 있습니다(롬은 저장소 밖에 둡니다):
```sh
gcc -O1 -std=gnu99 -Ilibretro-common/include -o /tmp/fgrom ../tools/harness/fgrom.c -ldl
# 입력 스크립트로 메뉴를 지나 대전까지 간 뒤(FGROM_SAVE/FGROM_LOAD 로 상태 저장·복원),
# interp/predict 모드로 돌리며 합성 프레임을 .565 로 떨어뜨리고(FGROM_PICK=<프레임>) OAM/문자RAM 도 덤프(FGROM_OAM/FGROM_CHR)
# (보간 모드는 에뮬레이션이 도는 호출에 중간 프레임, 다음 호출에 실제 N 을 내므로 하네스가 모드별로 합성 프레임을 가려낸다.
#  사무쇼2는 RTC 를 읽어 실행마다 갈라질 수 있다 — 비교할 땐 time() 을 고정하는 LD_PRELOAD 심을 쓴다.
#  FGROM_MULT=4|2 배수. 4배는 실제 호출의 그림도 옮기므로 FGROM_REF=<off 모드 dump_every=1 디렉터리> 로 기준 프레임을
#  주면 출력 프레임마다(두 위상 모두) 기준 N·N+1·N+2 와 대조한다. FGROM_DUMPALL=1 은 출력 프레임을 전부 떨어뜨린다)
/tmp/fgrom ./mednafen_ngp_libretro.so /path/rom.ngc /tmp/wd interp 600 "0-0:U" 0 0
```
사무쇼2 실측(2026-10-10): 체인 비트는 안 쓰고(모든 스프라이트가 절대좌표), 타일 번호는 슬롯마다 고유하며,
**포즈가 바뀔 때 같은 타일 번호에 새 그림을 올려 씁니다**(600프레임 중 84프레임에서 935조각). 그래서 번호만 보고
움직이면 포즈 교대 프레임마다 옛 그림이 새 배치의 중간 자리에 찍혀 깨졌고(실기 보고: 뉴트럴 숨쉬기에서 두드러짐),
지금은 문자 RAM 의 그림(16바이트)까지 같아야 같은 조각으로 쳐 그 프레임은 base 포즈를 온전히 그립니다.
단독 스프라이트·체인 그룹(다른 게임용)은 슬롯별로 짝짓되, 같은 타일 번호를 둘 이상의 조각이 쓰는 경우는 그 조각들이
모두 같은 벡터로 움직일 때만 믿습니다(자리 바꿈이면 정지).
체인 없는 메타스프라이트(사무쇼2 방식)는 「우선순위·팔레트가 같고 16px 안에 붙는 연속 슬롯」을 한 캐릭터(무리)로
묶어 강체로 움직입니다(묶음 규칙은 PocketCore 방의 ss2fg_consensus.patch 에서 가져옴). 무리 안에서는 조각을
**겉모습으로** 짝짓습니다 — 조각마다 다음 프레임 전체에서 플립·우선순위·팔레트·타일 그림(16바이트)이 같은 조각을
슬롯·타일 번호와 상관없이 찾아 그 거리에 표를 던지고(짝이 여럿이면 표를 나누고 넷을 넘으면 기권, 빈 조각도 기권),
최빈 이동량 하나로 포즈가 바뀐 조각까지 함께 옮깁니다(겉모습 짝짓기는 PocketCore 방 패치 3판 b38e05d 에서 가져옴).
슬롯별 짝짓기만 쓰면 조각이 끼어들어 번호가 밀린 프레임·포즈 교대 프레임에서 표가 하나도 안 나와 무리가 섰는데,
겉모습 짝짓기는 그대로 남은 조각으로 몸의 이동을 찾습니다(롬 실측 600프레임: 무리가 통째로 선 프레임 100 → 26,
움직인 조각 +17%, 두 방식이 다 벡터를 낸 조각의 어긋남 0). 1등에 표를 준 조각이 둘 미만이거나, 1등이 2등(1등의
±1px 창 밖)의 두 배가 안 되거나, 그림 있는 조각의 1/4 에 못 미치면 그 무리는 그 프레임만 정지(60Hz 와 같음) —
과반 규칙 대신 「뚜렷한 1등」을 쓰는 것은 같은 그림이 줄지어 선 효과(가로 6조각 중 4조각이 같은 그림)의 표가
±8·±16 으로 대칭으로 흩어져도 진짜 이동량이 1등이 되게 하려는 것입니다. 벡터를 쓰기 전에 「자리 + 벡터」에 같은
그림의 조각이 있는 수를 제자리와 견주어, 제자리가 같거나 많으면 쓰지 않습니다 — 머리 조각 하나가 슬롯 0 에 끼어들어
번호가 한 칸씩 밀리면 슬롯별 짝이 타일 간격(-8px)의 가짜 이동량을 내는 것(유파선택 대기 실기 보고, PocketCore 방
c0e2f79)을 막습니다.
**몸 위치(사무쇼2 RAM)**: 맞고 빙글빙글 날아갈 때처럼 포즈가 매 변화마다 통째로 새로 그려지면 겉모습이 같은 조각이
없어 겉모습 투표가 비고, 그 몸만 30Hz 로 끊겼습니다. 사무쇼2 롬일 때 코어가 CPU RAM 을 물려 주면(`ss2fg_set_ram`)
캡처마다 두 캐릭터의 몸 위치(P1 X 0x0E38·Y 0x0E3A, P2 +0x40, 카메라 X 0x176D, 대전 중 = 0x00A7 가 241)를 같이
적습니다. 게임은 RAM 을 먼저 바꾸고 다음 프레임에 그리므로 이 프레임 화면의 몸 위치 = 직전 캡처의 RAM 값입니다
(롬 실측: 몸 근처 조각의 겉모습 벡터와 1867:19 일치). 겉모습 투표가 비거나 표가 모자라거나 겹침 검증에 걸리면,
몸 팔레트(P1 = 0, P2 = 5)이고 무리가 몸 위치 근처(옆 40px, 위 16px ~ 아래 56px)일 때 몸의 이동량으로 무리 전체를
옮깁니다(지금 포즈를 궤적대로 — 회전 그림을 만들어 내진 않음). 겉모습 표가 몸 이동과 4px 넘게 어긋나면 우연한 짝으로
보고 몸을 따릅니다. 외톨이 조각도 같은 조각이 딱 하나면 그 거리, 아니면 몸 위치로. 롬 실측 600프레임: 무리가 선 조각
4360개(155프레임)가 살아나고 무리가 통째로 선 프레임 26 → 0, 어긋남 0 (PocketCore 방 30_ss2fg_body.patch 를 main 에 들임).
몸 위치는 RAM 물체 표(0x0E00 + 0x40·k: +0x36 종류(0xFFFF = 빈 칸), +0x38 X, +0x3A Y)의 칸 0·1 이고, 칸 2·3 은 그림자,
4~7 은 기술 이펙트·장풍입니다(캡처가 8칸을 모두 적습니다). 몸 팔레트가 아닌 무리(그림자·이펙트)가 겉모습으로 안 정해지면
그 무리 테두리에 가장 가까운(16px 안) 그림자·이펙트 칸의 이동량을 쓰되, 앞뒤 프레임에서 같은 종류로 쓰인 칸만, 그리고
다음 프레임의 같은 팔레트 조각 테두리 가운데가 물체와 같이(±2px) 움직였을 때만 믿습니다(물체 자리가 그림 기준점이 아닌
이펙트가 많아 이 검사가 없으면 흔들립니다). 캐릭터 칸은 이펙트에 안 씁니다. 롬 실측 600프레임: 그림자 417·이펙트 39 조각
(86프레임)이 더 살아나고 어긋남 0 (PocketCore 방 40_ss2fg_objects.patch 를 main 에 들임).
다른 롬은 RAM 을 안 물려 지금과 같습니다.
알려진 한계: 무리·체인은 강체로만 움직입니다(관절 움직임은 보간 안 함). 코어가 선언하는
60.25fps 는 에뮬레이션 실제 주기(199줄×515틱 ≈ 59.95Hz)와 0.5% 어긋나는 upstream 값 그대로입니다.
