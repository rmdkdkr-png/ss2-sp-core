## 2. 링 주입 — 필살기 발동 9 → 3

게임은 방향 입력을 `0x0CB8~0x0CCE` 에 2칸 간격으로 쌓는다(최신이 `0x0CC8`, 새 입력이
오면 앞으로 2씩 내려감). 커맨드를 **직접 써 넣고** 마지막만 실제로 입력하면 방향키를
프레임마다 넣을 필요가 없다.

```
마지막 방향이 → 또는 ←   →  앞 칸만 박고, 마지막 방향+버튼을 **같은 프레임에** 실제 입력
마지막 방향이 대각(↘·↙)  →  **전부 박고 버튼만** 실제 입력 (방향 얹으면 안 나감)
```

방향과 버튼을 같은 프레임에 내보내야 한다. 방향을 2프레임 먼저 내보내면 그 사이 링이
밀려 안 나간다 — 회귀가 18/23 → 2/23 으로 무너졌던 원인이 이것이었다.

**검증**: 18캐릭터 127기술에서 주입이 손 커맨드보다 못한 경우 **0건**. 3회 반복 재현.
황물기는 화면 픽셀로도 확인(같은 기술 0.4% 차이 / 다른 기술 10% 차이).

**대가**: 강 경계가 SP 12 → 6 으로 당겨진다. 버튼 스텝이 프레임 0 부터 돌아 SP 길이가
곧 버튼 길이가 되는데 게임 문턱은 버튼 8프레임 고정이라 그렇다. `RING_HOLD_BIAS` 로
12 까지 밀어 봤으나 위상1 에서 강이 아예 안 나온다(발동이 위상마다 3/2 로 갈려
버튼 길이가 1프레임 어긋나는데 문턱은 고정) — 그래서 BIAS 는 0 이다.

## 3. 강 기본기 즉발 — 8~9 → 2~3

게임의 **버튼 홀드 카운터**를 찾았다.

```
0x0C76  펀치      누르는 동안 2프레임에 1씩 오르고 놓으면 0
0x0C77  킥        값 4 = 버튼 8프레임 = 강 문턱
```

버튼을 2~3프레임만 넣고 **매 프레임 검사해 3 미만이면 3 을 박는다.** 다음 프레임에
게임이 4 로 올려 문턱을 넘는다. 4 이상을 박으면 게임이 되돌려 안 된다.

**매 프레임 검사가 핵심.** 특정 프레임에 한 번만 박으면 게임의 2프레임 주기 어느 쪽에
걸리느냐로 갈려 수율이 50% 였다(캐릭터마다 한쪽 위상만 성공). 매 프레임 검사로 100%.

**검증**: 18캐릭터 × 강펀/강킥 × 두 위상 = **72/72**. act·피해가 12프레임 대조군과
완전히 같고(하오마루 강펀 16, 마이 강킥 4 까지) 발동이 **정확히 6프레임** 빠르다.

이 카운터는 **대조군 없이 찾으면 시간 카운터에 묻힌다.** 버튼 누름 / 안 누름을 같은
프레임에 비교해야 나온다. 처음엔 "게임이 버튼 홀드를 메모리에 안 남긴다"고 잘못 결론냈다.

## 4. 롬 패치 — 한 바이트

홀드 카운터를 읽는 PC 를 코어에 훅을 넣어 잡았다(`loadB` 에서 주소 일치 시 `pc` 출력).
그 근처 코드에 `3F 04`(CP 4) 패턴이 있고, 그 `04` 가 강 문턱이다.

```
롬 오프셋 0x000D4E :  04 → 02
```

| 값 | 강이 나오는 버튼 길이 | 강 발동 |
|---|---|---|
| 4 (원본) | 8프레임 이상 | 9 |
| 3 | 6 이상 | 7 |
| **2 (패치)** | **4 이상** | **5** |
| 1 | 2 이상 | 3 (약을 사실상 못 냄) |

`0x000BAD` 에도 `3F 04` 가 있지만 그쪽은 무관하다(다른 문턱).

**모든 정상 판본이 같은 자리에 같은 바이트**다 — 한글패치·[!]·a1·a2·h1·h2·t1·t2 전부
`03 F4 E1 3F 04 6E 03 8C`. b1 만 다르다(불량 덤프).

IPS: `~/ss2/release/svc_faststrong.ips` (14바이트). 패치본 롬 `~/ss2/rom/svc_fast.ngc`.

**착지 선입력은 패치 롬에서 값이 달라진다** — 패치 롬 + 떼기 1프레임이 착지 +5~6 으로
가장 빠르지만 창이 좁아진다(착지 7~4프레임 전만). 순정 + 떼기 2 는 +11~12 지만 넓다
(착지 4프레임 전 ~ 5프레임 후). `SVCSP_LANDCUT` 으로 고른다. 지금 기본은 2.

## 5. 판정 규칙 — 이걸 안 지키면 결론이 다 틀어진다

| 값 | 쓸 수 있나 |
|---|---|
| **뱅크 `0x09AD`** | **못 쓴다.** 같은 입력이 2프레임 위상에 따라 21↔22 로 갈리고 황·독이 둘 다 21 이 되기도 한다 |
| **피해** | **단독으로 못 쓴다.** 거리·타이밍에 흔들린다 |
| act `0x0968` | 쓸 수 있으나 완전하지 않다. 쿄 `175` 가 팔청·죄읊기·누에잡기 셋에 걸리고, 가일 `2`(소닉붐)는 뒤로 걷기와 겹친다 |
| **화면 픽셀** | **최종 잣대.** 손 커맨드판과 발동 프레임에 정렬해 비교 |

**손 대조군의 칸당 프레임에 주의.** 3프레임이면 짧고 5프레임이면 커맨드 창(8프레임)을
넘겨 실패한다. 이 때문에 「성공률 20%」라는 엉뚱한 집계가 나왔다.

act ↔ 기술 이름 표 생성: `scratchpad/actmap.sh` (18캐릭터 전 기술을 손 커맨드로 냄).

## 7. 남은 일

**0-a. 착지 선입력 × 강 즉발 충돌 (최우선 — 사용자 요구사항)**
   사용자 목표: **점프 공격 히트 → 착지 즉발 강펀 → 캔슬 필살기.** 기술 정배는
   중립=파동권 · 앞=승룡권 · 뒤=용권.
   현상: `SVCSP_FASTSTRONG=1` 이면 착지 강펀이 **아예 안 나간다**(끔이면 착지 +12).
   물리 엣지가 공중에서 소진돼 즉발 경로가 착지에서 안 걸린다. 착지 재누름 프레임에
   홀드 카운터(0x0C76/77) 주입을 추가해 봤지만 **효과 없음** — 원인이 다른 데 있다.
   재현: `scratchpad/jland.sh`. 점프킥은 히트하는데(피해 6) 착지 강펀이 늦어 콤보 1.

**0-b. 하오마루 반전 스테이트에서 필살기 전면 무발동**
   사용자 스테이트(/tmp/a1.st, [a1] 롬)에서 손 커맨드 236/214/623/421 **전부 무발동.**
   걷기·평타는 된다. 뱅크 1 에 영구 고정. 엔진·미러 탓 아님(쿄 flip 은 정상).
   다음: 하오마루 반전 세이브를 직접 구워 같은 증상인지 대조. 재현: `scratchpad/haoh2.sh`, `stuck.sh`.


1. **레오나가 아무것도 안 나간다** — 18캐릭터 시험에서 혼자 0타 0피해. 원인 미상
2. 회귀 실패 5개 중 진짜는 2개 — **강펀캔슬**(뱅크 22 는 뜨는데 피해 0)·**밀착**(무발동).
   나머지 3개(앞쥠·앞뗌·반전앞쥠)는 기대식이 뱅크로 적혀 있어 생기는 가짜 실패
3. `CHARGE_FRAMES` 를 실측값 **6** 으로 (지금 40. 게임의 진짜 모으기 요구는 6프레임)
4. 강 경계 6 이 손에 맞는지 — 사용자가 지정했던 값은 12 였다
5. 착지 선입력 값(`SVCSP_LANDCUT`)을 패치 롬 기준 1 로 할지
6. 버튼 구성을 **A / B / SP / A+B 4키**로 줄이는 계획은 아직 손대지 않았다

## 9. 앱 연동 (PocketCore v3.47, 2026-09-02)

- 앱이 **한글패치를 릴리즈에서 자동 다운로드**한다: KrPatch 고정 태그 \pocketcore\ 의
  \patches.json\ (게임 id → 최신 IPS 주소·판) → \PocketCore/patch/\ 에 저장,
  Patcher 가 동봉 assets 보다 이쪽을 먼저 쓴다. 판이 바뀌면 도장(:P판)이 어긋나 재패치.
- Games 표에 **KOF R-2**(표식 \KOF R2\)·**아랑전설 퍼스트 컨택트**(\RB_F_CONTACT\) 추가 —
  표식은 롬셋 헤더 0x24 실측. 둘 다 svc 코어(원버튼 엔진은 SVC 롬이 아니면 잔다)로 돈다.
- patches.json 은 배포 스크립트(pub_pocketcore.py)가 KrPatch 릴리즈 **실태를 훑어** 자동 생성 —
  게임별 자산 이름 정규식으로 최신판을 고른다. 새 한패를 올리면 앱 쪽은 손댈 것 없다.

### v3.48 — 컨텐츠 외장화 (앱 업데이트와 분리)

- **APK 재설치는 앱이 바뀔 때만.** 코어·음성팩·한글패치는 각자 고정 태그 릴리즈에서

  dlopen 이 안 되는 기기가 많다. 코어 선택 순서: 수동 PocketCore/cores/ → 내부 자동 → 동봉.
